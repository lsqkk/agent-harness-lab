    模型提出，Harness 执行

    01 一次工具调用到底发生了什么？

    用户问「这个项目用什么主题」。宿主程序把问题和工具定义一起发给模型。工具定义告诉模型有哪些函数、参数怎么填。模型返回一个带 ID 的 tool_calls 请求，程序据此查找本地函数，校验参数，读取样例文件。

    assistant  tool_calls[0]
  id: read-1
  name: read_file
  arguments: {"path":"config/app.json"}

tool
  tool_call_id: read-1
  content: {"ok":true,"content":"…","revision":0}

    Harness 把助手的调用消息和工具的结果都放进下一轮请求，用 tool_call_id 把结果和调用配对。模型这时才拿到文件内容。如果它继续发出工具调用，程序继续处理。如果它给出答复，循环结束。打开实验中的「请求上下文」可以看到每轮的完整消息和工具定义。

    02 最初的油猴脚本做到了哪一步？

    旧版在网页回答里找 [[COMMAND={…}]]，用浏览器脚本把请求发给本地 Node.js 桥接器。桥接器读文件，你再把结果粘贴回对话。工具调用已经有了形状，结果回传由人完成。后来本地 CLI 草稿让这一步自动运行，但仍需要从网页文本猜测命令和回复边界。

    结构化工具调用把函数名、参数和调用 ID 放进协议字段。它解决了如何传递调用，执行权限仍由宿主判断。反向代理主要负责转发请求，Harness 还管理下一轮模型应该看到什么、何时执行工具、何时暂停等状态。

    03 什么值得放在模型外面？

    参数与权限
    工具名必须注册，参数必须合规，路径必须属于样例项目。这些条件在工具执行前由程序检查。
    错误与反馈
    FILE_NOT_FOUND 是一次可见的工具结果。模型可以根据它改用 list_files，再读取正确路径。
    审批与并发
    写入先生成替换预览。审批时重新检查文件修订号。若文件已被修改，旧预览返回 CONFLICT，模型需要重新读取和提案。
    预算与退出
    工具调用数和模型请求轮次各有上限。超过工具预算时拒绝整批新调用，避免只执行一半。
    轨迹与回放
    轨迹保存模型请求、可见响应、工具结果和每步文件快照。回放按顺序展示已记录的事件。想验证另一种审批决定，重置实验并重新运行。
